## Implementation sequence

1. Locate frontend source and integrate shared request/context/question/editor/action APIs with generated types/examples. Preserve finite event replay and continue following edits after generation completes.
2. Build labelled evaluation sets across five intents and compound/ambiguous/adversarial/partial-context cases. Separate train/dev/holdout examples and pin dataset/prompt/model/flow versions.
3. Measure routing/clarification correctness, evidence grounding, temporal extraction, missing facts, unsafe actions and outcome honesty; agree thresholds before evaluating the release.
4. Run browser UI scenarios for original examples, edit/review/send, stale conflict, cancellation, reconnect and outcome_unknown. Copy/Insert/Save/Send must display distinct states.
5. Add crash/recovery and deployment-role integration tests; summarize failures, exclusions, latency/cost and raw redacted evidence. Fix failures before claiming initial all-intent completion.

## Acceptance assertions

Implement independent tests for these behaviors. Record each assertion in the checkpoint;
do not mark a live assertion passed using only a mock. Apply all relevant QUALITY-GATES checks.

- **B18-A1:** All original user examples pass on actual frontend/backend with controlled data; third-message answer stays bound after navigation.
- **B18-A2:** Browser close/reconnect during generation/approval/send resumes accurate state without duplicate requests/actions.
- **B18-A3:** Failure injection spans OAuth revocation, model failure, Google timeout, expired lease and migration compatibility.
- **B18-A4:** Held-out model quality is reported with denominators, per-intent results, ambiguity cases and manual review; synthetic tests are not counted as live accuracy.
- **B18-A5:** No unsupported route is presented as successful; review and send controls bind the displayed exact revision/recipients.
