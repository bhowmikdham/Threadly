# Classification backend: deployment and frontend handoff

The Haiku 4.5 classification service is **deployed and enabled** on the public
Threadly API. Activation completed at **2026-10-06 15:26:26 UTC** (7 October in
Melbourne). Backend commit `7b2c2770cb1906b4c39af8cce864bb09ec05805f` was merged
into `release/backend` through [PR #105](https://github.com/bhowmikdham/Threadly/pull/105).
This record covers the service; the frontend team owns request scheduling and badge UI.
No extension or website implementation was changed or deployed.

## Frontend entry point

```http
POST https://api.threadly.au/threads/{gmail_thread_id}/classification
Authorization: Bearer <Threadly access JWT>
Content-Type: application/json

{"time_zone":"Australia/Melbourne"}
```

The backend retrieves the authenticated account's live Gmail thread, invokes the
pinned Haiku visual Flow, validates labels/evidence, independently refetches the
thread and rechecks the session. Clients send only the thread ID and timezone.
They cannot select a model or submit authoritative email content.

- Reply: `needs_reply` is a boolean, independent of the action label.
- Priority: `High`, `Medium`, `Low`.
- Category: `finance_payments`, `hr`, `it`, `legal_contracts`,
  `meeting_scheduling`, `other`, `projects`.
- Action: `approve`, `attend`, `complete_submit`, `edit`, `no_action`, `reply`, `review`.

Category, priority and action labels retain the saved BERT mappings, including IT.
The BERT user-intent classifier remains separate; no trained binary reply model
was found. The [artifact snapshot](../../ml/evals/classification/bert-labels.json)
records the comparison and native model IDs.

Use the [full contract](README.md), [TypeScript types](types.ts),
[response schema](response.schema.json) and [synthetic UI fixtures](frontend-fixtures.json).
Render labels only for `status=classified`. Review/skipped states have null labels;
errors must never become default No Reply/Low/Other badges. Respect result expiry,
account/thread changes, `Cache-Control: no-store` and 429 `Retry-After: 5`.
The result lifetime is five minutes; it does not guarantee the Gmail thread remains unchanged.

## Runtime configuration and operational limits

The active service uses `CLASSIFICATION_TRANSPORT=bedrock_flow`, concurrency 2,
validity 300 seconds and the retained Haiku prompt 1.0.1 / Flow version 1 target.
The Australian Haiku 4.5 profile is pinned. Nova's Flow and dedicated resources
remain retired; no fallback runs. The application role received the scoped
`ThreadlyClassificationHaikuFlow` inline policy without replacing existing permissions.

There is one API process, so two is the current deployment's classification-call
limit. It does not limit other assistant calls and is not a distributed limiter.
There is no shared cache, deduplication, stored classification or saved correction.
Existing `/threads` responses, database `needs_reply` values and mailbox-wide filters
are not populated by this endpoint. Plan capacity before adding API workers or replicas.

The live sample proves integration and contract behavior, not label accuracy.
The synthetic mismatch was `request-already-resolved`: Haiku chose Medium priority
where the fixture expects Low. Twelve seed cases do not establish a production
accuracy threshold. A broader human-labelled evaluation remains product quality work.
Logout/reconnect races, cancellation and source-change rejection were exercised in
isolated integration tests; this live smoke did not revoke the user's sessions,
send email or modify Gmail/Calendar content.

Protected configuration snapshots, target manifest, database backup, operator
scripts, full synthetic report and activation receipt are retained in the host's
restricted classification deployment audit folder. See the
[deployment/activation/rollback runbook](DEPLOYMENT.md). Rollback disables the
classification flag and recreates only the API; no label-data rollback is required.
