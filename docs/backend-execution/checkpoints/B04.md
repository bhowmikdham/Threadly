## Behavior and decisions

Explicit exact-payload approval persists approval, state, queue and event together.
The public route is present but cannot accept new approvals while the sender is
uninstalled. Internal tests use an explicitly enabled service and fake dispatcher;
no HTTP or environment argument enables writes. Rejection/cancellation are usable
public owned operations with durable idempotent receipts. Late cancellation only
records intent, retaining executing/unknown state and recovery job/attempt.

Read responses distinguish historical decision/approval from current action state.
Saved MIME is never rebuilt. Approval rechecks artifact/current revision, effective
context, Google identity/version/grants, credential metadata and expiry while locks
fence source/auth publication. No provider calls or helper commits.

Detailed API, diagrams and implementation map: [action approval](../../action-approval.md).

## Focused second review

- Action ownership checked before replay; action/operation/body bound in request hash.
  Approval uses existing owner-wide key namespace; cancel/reject use distinct namespaces.
- Lock order task → action → account → job/attempt. Sync/auth publication never
  acquires task/action afterward; future deletion and executors must preserve order.
- Cached thread/message rows refreshed; captured scopes compared as well as account
  version. No network work under locks; future dispatch still needs fresh checks.
- Historical approval replay occurs before readiness checks, performs no transition
  and cannot resurrect a closed job. Nested action state is authoritative for UI.
- Late cancel does not change action version/state, clear leases or delete attempts.
  Its immutable receipt and task event commit together. Rejection is proposed-only;
  approved work uses cancel. Expiry/Google disconnection do not prevent withdrawal.
- Public availability remains false; request cannot inject internal enablement.
  DraftReview stays separate. Approval ID/historical authorization is not proof of delivery.
- Queue insertion follows approval/guarded state; rollback covers all effects. Known
  expiry guard errors become sanitized 409 blockers, with caller rollback required.
- Additive receipt migration preserves preexisting draft, payload, approval and attempt;
  actual immutable/FK/check guards and refusal to erase decision history tested.
- Events/receipts contain IDs/state/request metadata, no mail body/recipient/token.
- Remaining live gates: OAuth configuration, dedicated sender/reconciliation, Gmail
  threading/Bcc delivery, exact frontend approval UI and retention/recovery policy.
