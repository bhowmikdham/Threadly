## Implementation sequence

1. Add owned calendar preferences: IANA zone, selected calendar IDs, working periods, buffers, notice/default duration and policy/version. Validate ranges and expected_version.
2. Implement calendar connection/list endpoints and paginated REST client with httpx transports and granted capability checks. Validate selectable calendars/ACLs; freebusy access and event-write access differ.
3. Implement bounded freebusy query for authorized calendar set/time window, normalized aware instants and per-calendar errors/omissions as unknown.
4. No DB transaction spans Google reads; recheck preference/capability version before persisting evidence. Store minimal source/check time and expiry metadata.
5. Choose explicit maximum horizon, calendar count and interval count with tests/config docs. Do not expose arbitrary URLs or calendar IDs from model output.

## Acceptance assertions

Implement independent tests for these behaviors. Record each assertion in the checkpoint;
do not mark a live assertion passed using only a mock. Apply all relevant QUALITY-GATES checks.

- **B12-A1:** Partial scope, revoked grant, non-writable calendar, unknown calendar and other-owner preference IDs fail appropriately.
- **B12-A2:** Concurrent preference updates conflict instead of silently overwriting timezone/calendar choices.
- **B12-A3:** Freebusy response with per-calendar error or missing entry returns unknown even if other calendars are empty.
- **B12-A4:** Malformed naive times, reversed ranges, excessive horizon/calendar count and pagination cycles are rejected.
- **B12-A5:** Provider latency does not hold DB locks; changed preferences during fetch invalidate evidence.
