## Active behavior

- Successful results remain valid for **one hour**, subject to immediate client
  invalidation when the thread/account changes. This is display validity, not a
  backend cache.
- Classification admits **two concurrent requests** before fetching Gmail and
  allows **eight model attempts per rolling minute**, including retries.
  Excess calls return `429 classification_busy` with the actual `Retry-After`.
- Transient read-only inference failures retry at most three attempts with
  jittered backoff. Model/prompt/Flow versions and label semantics are unchanged.
- Documented Gmail rate-limit 403s and 429s receive bounded read retries and a
  distinct cooldown response. Genuine or unknown 403s remain access denials.
  The historical intermittent 403s did not contain enough logged detail to prove
  their cause; new logs retain only safe reason codes.

AWS still reports **10 Haiku requests/minute**. Eight classification attempts leave
limited headroom for other model consumers; this is a process-local budget, not
an account-wide distributed limiter. A cold inbox with 22 uncached threads can
still take over two minutes. Raising concurrency alone cannot change that cap.
[Support case 179141544300892](https://support.console.aws.amazon.com/support/home#/case/?displayId=179141544300892&language=en)
requests 120/minute and investigation of AWS's applied/default quota discrepancy.
No capacity approval is claimed.

## Rollback and correction during this rollout

The first release passed CI and health checks but failed the authenticated Gmail
smoke: copying Content-Encoding onto already decoded response bytes caused double
GZIP decoding. It was rolled back to `bc12ef106659f5ac8b5b79890e0887f1431e29ea`;
live Gmail listing passed on the restored release. PR #130 reads Retry-After from
the original headers without applying content decoding again. The corrected image
was tested privately against live Gmail before public redeployment.

Protected backups and deployment receipts are retained in the host's restricted
`classification-reliability-20261008-corrected` audit folder. Use the existing
[rollback runbook](DEPLOYMENT.md); no classification migration or label-data
rollback is required.
