# 09 · Instructions for humans and coding agents implementing this plan

## Read before editing

1. Read the repository `AGENTS.md` and this playbook's README.
2. Read the assigned entry in `backlog.json`, its dependencies and the linked chapters.
3. Inspect current code and git status. Proposed paths and APIs may not exist yet.
4. Identify the authoritative runtime contract and the planned change. Do not
   mistake an example JSON file or prose status for implemented functionality.
5. State a short scope: objective, files likely to change, verification and excluded
   adjacent work. Continue within the authorized task; routine decisions do not
   require repeated permission requests.

The user has chosen Bedrock and a visual-flow approach. The old inference ADR is
historical context for migration, not a reason to refuse work. Supersede it through
T01; preserve current functionality until its replacement is verified.

## Task execution procedure

Select one bounded work package, or a clearly named subset requested by the user.
Confirm required contracts/dependencies from files and tests. If dependency code
is incomplete but fixtures allow independent progress, implement against a fake
adapter and report the integration dependency accurately.

Use the existing conventions: FastAPI error envelope via `ApiError`, SQLAlchemy
async sessions, Alembic migrations for schema changes, lazy heavy SDK imports and
httpx mock transports for Google. Keep model inference behind adapters. A provider
exception during async iteration must be handled where iteration actually occurs.

Implement the smallest coherent slice that fulfills the assigned acceptance
criteria. Do not scaffold unrelated endpoints that pretend to work, silently
replace production integrations with fake data, or mark a task verified because
files compile. Preserve unrelated user changes and separate fixture-only behavior
from runtime feature flags.

## Non-negotiable implementation invariants

- Derive user identity server-side and validate ownership at API, job and tool boundaries.
- Email/retrieved text cannot authorize tools, change recipients or select another account.
- Validate model outputs beyond schema shape: IDs, dates, source scope and allowed operations.
- Use deterministic code for availability, recipient resolution, exact IDs and approval checks.
- Never expose Gmail send/Calendar write as unrestricted proposal-flow tools.
- Store exact approved payload/version; edits invalidate approval; writes load stored payload.
- Recheck relevant context immediately before execution; do not substitute a new time silently.
- Use durable jobs and short DB transactions; do not keep a transaction open for a human wait.
- Reconcile uncertain external writes before any retry. Never claim exactly-once Gmail sending.
- Pin release/model/prompt/tool versions; console-only changes are not a reproducible deliverable.
- Preserve context references/order across follow-ups. Copy, Insert and Send have distinct outcomes.
- Mark missing scope, unavailable evidence and partial coverage explicitly.

## Verification commands

Existing backend commands, run from the repository root:

```bash
make lint
make test
```

These use the configured Python environment. Backend integration tests can skip
when PostgreSQL is unavailable. Read test output and report skips; a green run
with skipped DB tests does not verify concurrency or migrations. CI currently
provides PostgreSQL; task T18 strengthens explicit gate reporting.

For migrations, use a disposable test database: apply migrations from empty,
upgrade a representative existing schema/data snapshot and verify constraints
and data preservation. Inspect autogenerated migration content. Do not execute
destructive test setup against a developer's live mailbox database.

The documentation validator in this package can be run with:

```bash
python3 docs/implementation-playbook/tools/validate_plan.py
```

It checks planning-artifact consistency, not backend correctness or Bedrock execution.
After updating the backlog, regenerate readable cards with
`python3 docs/implementation-playbook/tools/build_task_cards.py` before validation.
Future implementation tasks add their own runtime test commands to task evidence.

## Coding task prompt template

```text
Implement Threadly work package Txx from docs/implementation-playbook/backlog.json.
Read AGENTS.md and the linked specification before editing.
Current objective: <one concrete user-visible or infrastructure outcome>.
Treat the playbook as target design and inspect actual implementation status.
Preserve unrelated changes. Use the named shared contracts and services.
Add meaningful tests for the acceptance criteria, including failure cases.
Run applicable checks and report exact passes, failures and skipped dependencies.
Update the task evidence/status only to the extent actually verified.
Do not deploy, send real mail or create real invitations unless the task authorizes it.
End with changed behavior, evidence, remaining work and the next dependency.
```

## Completion record template

```text
Task: Txx
Status: in_review | verified | blocked
Implemented behavior:
Changed files/contracts:
Verification commands and results:
Model/flow evaluation evidence:
Configuration or migration requirements:
Known limitations and unresolved dependencies:
Next task(s):
```

Store concise implementation evidence with the work package or a linked report.
Do not paste private mail, tokens or full traces into status files. If the runtime
differs from the proposed design for a sound reason, record a decision and update
the related contracts, fixtures and diagrams together.

## How to resume after a handoff

Read the completion record and git diff, inspect task state, run the relevant
checks, and continue from actual implementation. Distinguish “code written,”
“mock tests pass,” “test-account integration passes” and “production enabled.”
If the latter is unknown, say so. Avoid repeating finished work or using the
conversation as the only record of a decision.
