## Implemented behavior and contracts

- `POST /assistant/tasks/{id}/inputs` accepts a strict typed answer to the current
  owned question. It locks the task, verifies question/task/input versions, route
  hash and expiry, consumes once, saves immutable input history and atomically requeues.
- Original instruction/request hash, initial context/draft input and generation
  release remain unchanged. Effective context/envelope/fields are explicit. Worker
  resumes the saved goal without classifying the answer. Provenance includes the
  input version and pinned `typed-continuation-1.0.0` contract.
- Questions support source/UI selection, explicit recipient/reply target, timezone,
  duration, date/time phrases and AM/PM. Fresh source must remain in the originally
  bound thread; UI answers must resolve the requested mapped message. Unknown fields
  return explicit unsupported outcomes. Raw instructions/approvals/Flow IDs are rejected.
- Partial answers produce a new versioned question. Maximum five answer rounds,
  three worker attempts per cycle and 24-hour expiry are pinned defaults. New waiting
  tasks can cancel; old tasks keep their historical terminal behavior.
- Date/time answers preserve the original scheduling intent, but no Calendar handler
  is installed. Complete scheduling inputs therefore end at `workflow_not_available`.
  No compound engine, BERT invocation, mail send or event creation is claimed.
