## Behavior and decisions

Actual token-response scopes, verified userinfo identity, connection state and
separate permission/token versions persist. Legacy tokens remain encrypted and
unchanged; legacy grants/verification stay unknown. Capabilities require stored
evidence and implemented handlers; send/Calendar remain false. This is not a live
provider validity probe.

The old stateless exchange is replaced with one-use state plus required S256 PKCE.
Begin/reconnect record ten-minute state, exact allowlisted callback and optional
owned account version; exchange consumes it before Google network calls. Reconnect
cannot switch subjects or use a pre-disconnect account version. Concurrent first
login handles the unique subject race. Source email/model text has no role in auth.

The inspected frontend (`43694c1`, `sidepanel.tsx`) uses Chrome getAuthToken directly,
not the backend exchange. The new handshake is explicitly documented as a client
contract change, with frontend wiring deferred. No compatibility claim for passing
that access token as a code. Callback/client registration must be tested live.

Credential refresh uses dedicated read/write sessions around the HTTP request and
fences late results by token version. It never commits caller work. Routine refresh
preserves permission version; grant change/reconnect/disconnect advances it.
`invalid_grant` locally disconnects; transient/configuration failures do not erase
credentials. Local disconnect is not provider revocation or Threadly session logout.

## Focused second review

- Reviewed code exchange vs the actual frontend snapshot before defining state/PKCE.
  No permissive stateless path retained; errors omit raw inputs/provider bodies.
- Userinfo must provide a bounded subject, valid basic email shape and true email
  verification. Auth derives subject from Google, never client-supplied user data.
- Callback must exactly match configured HTTPS allowlist; malformed URLs fail safely.
  Public begin only requests identity + Gmail read, never arbitrary scopes.
- State consumption commits independently before provider calls, so rollback and
  timeout cannot reuse authorization state. One consumer wins under row lock.
- Reconnect checks current subject/version under the user lock after network calls.
  Token refresh closes its credential-read transaction before HTTP, then fences
  persistence; caller pending data is never flushed or committed by that helper.
- Separate permission/token counters prevent routine renewal from invalidating
  exact actions. Future action code still needs pre-dispatch source/version rechecks.
- Preserved no-replacement refresh token behavior and explicit grant reduction;
  corrected seed's blanket treatment of HTTP 400 as revocation.
- Added typed public capability schema and honest stored-evidence readiness wording.
- Live consent, configured callback, provider revocation, auth rate limits and scheduled
  state retention remain release gates; no broader production-readiness claim.
