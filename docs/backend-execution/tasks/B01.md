## Implementation sequence

1. Extend token response parsing and persistence with actual grants, verified account identity, connection/revocation state and a monotonic capability/account version. Legacy unknown grants stay unknown; do not auto-grant send or Calendar.
2. Separate token network refresh from caller-owned transactions. Avoid internal commit of unrelated action work; preserve valid refresh tokens when absent in a response and fence concurrent refresh/disconnect.
3. Inspect actual extension OAuth flow; validate redirect allowlist, state/PKCE responsibility, userinfo identity and email verification before connecting accounts. Do not bolt on incompatible untested auth parameters.
4. Add GET /assistant/capabilities with implementation/flag/scope/source readiness, and incremental-consent/reconnect contract. Sanitize upstream errors and logs; no raw token endpoint bodies.
5. Update config/env examples, auth API docs and migration tests. Calendar scope requests must be deliberate; alias/send-as support remains unavailable until verified.

## Acceptance assertions

Implement independent tests for these behaviors. Record each assertion in the checkpoint;
do not mark a live assertion passed using only a mock. Apply all relevant QUALITY-GATES checks.

- **B01-A1:** Partial grant, absent scope metadata, revoked access and grant reduction never advertise unavailable send/calendar capability.
- **B01-A2:** Refresh without a replacement refresh token preserves the original; concurrent refresh/disconnect cannot restore a revoked connection.
- **B01-A3:** Wrong account subject, invalid redirect, replayed state or failed verifier is rejected according to the actual OAuth integration contract.
- **B01-A4:** Provider error body containing synthetic tokens does not appear in API errors/log capture.
- **B01-A5:** Caller rollback after token retrieval does not accidentally commit an unrelated pending action; migration preserves encrypted legacy tokens.
